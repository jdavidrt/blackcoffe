# BlackCoffe — Comprehensive Production Audit

_Date: 2026-04-21 · Branch: `claude/friendly-burnell-b334da`_

## Context

BlackCoffe is a single-tenant café order/payment management system (Express.js + MySQL + React/Vite) running in production on Render.com with a DigitalOcean MySQL. This audit was requested to map integrity, security, race-condition, business-logic, UX, scalability, and performance risks before scaling. All database inspection is **read-only** (SELECT / SHOW / DESCRIBE / EXPLAIN only) per operational constraints.

This is a **findings document**, not an implementation plan. Each finding includes location, severity, description, and a concrete recommendation. Verified against the current code. Note: CLAUDE.md's "no try-catch" claim is outdated — a global error middleware now exists at `server/index.js:40-46`.

---

## Severity Legend
- **CRITICAL** — data-loss, auth-bypass, or money-integrity bugs. Fix this sprint.
- **HIGH** — exploitable security gap, or certain failure at moderate scale.
- **MEDIUM** — latent correctness / UX / perf risk.
- **LOW** — code hygiene, cosmetic, or future-proofing.

## 1. CODE INTEGRITY & DESIGN

### 1.1 CRITICAL — Deposit delete is not transactional
**Location:** `server/controllers/deposits.controllers.js:71-146`
**Description:** `deleteDeposit` runs 4 independent statements (soft-delete → fetch → N-row loop UPDATE → order UPDATE) on the shared `pool` without `BEGIN/COMMIT`. A crash, connection drop, or concurrent write between steps leaves cumulative totals (`lastDeposit`, `newDeposit`, `dueOnDeposit`) inconsistent with the `orders.deposit` field. Money integrity depends on this loop completing atomically.
**Recommendation:** Use `pool.getConnection()` → `conn.beginTransaction()` → queries → `conn.commit()` / `rollback()`. Also collapse the per-row loop (line 120-130) into a single `UPDATE … CASE depositId WHEN … END` to remove the N+1.

### 1.2 CRITICAL — `createDeposit` is not transactional with the order update
**Location:** `server/controllers/deposits.controllers.js:42-69` + `client/src/pages/CollectOrderForm.jsx:219-233`
**Description:** The client calls `createDeposit` then separately `updateOrder` (`orderUpdate.deposit / paid / paidAt`). A network error between the two calls leaves a deposit row with an unchanged `orders.deposit` — the deposit reappears to the user after reload as "missing". The `try/catch` in the client (line 227-233) shows an alert but does not roll the deposit back.
**Recommendation:** Expose a single backend endpoint `POST /orders/:id/deposits` that inserts the deposit row AND updates `orders.deposit/paid/paidAt` inside one transaction. Delete the client-side "two-call" pattern.

### 1.3 HIGH — Order-merge race allows two unpaid orders per client
**Location:** `client/src/pages/OrderForm.jsx:85-90, 149-157`
**Description:** Business rule #1 (CLAUDE.md) requires *one* unpaid order per client. Enforcement is in the browser — client calls `getUnPaidOrdersbyClient`, then either `updateOrder` (merge) or `createOrder` (new). Two tabs / two staff members submitting concurrently both see "no unpaid order" and both create one. Nothing in the DB or server prevents it.
**Recommendation:** Enforce at the backend. On `POST /order`, run `SELECT … FOR UPDATE` on the client's active orders inside a transaction and merge server-side. Also add a partial unique index: `CREATE UNIQUE INDEX ux_one_unpaid_per_client ON orders (clientId) WHERE paid=0 AND isAbandoned=0` (MySQL requires generated-column workaround).

### 1.4 HIGH — `collectedBy` stores the mall name, not the user
**Location:** `client/src/pages/CollectOrderForm.jsx:300, 312`
**Description:** Both the paid and unpaid setOrder branches set `collectedBy: order.mall` (e.g. `"Unilago"`). Audit trail for "who collected this payment" is permanently wrong. CLAUDE.md § "Known Bug" flags this but it is still live.
**Recommendation:** `collectedBy: localStorage.getItem('user') || 'Unknown'`. Longer-term, add authenticated middleware so the server stamps it instead of trusting the client.

### 1.5 HIGH — Item-ID collision risk
**Location:** `client/src/pages/OrderForm.jsx:299`
**Description:** `id = product.id + ' ' + dayjs().format('HH:mm:ss DD/MM/YY')` gives a one-second resolution. Rapid double-clicks or a +1 keypress inside the same second produce duplicate item IDs — which `hasDuplicateItemIds` on the server then rejects with HTTP 400, silently losing the user's action.
**Recommendation:** Append milliseconds (`HH:mm:ss.SSS`) or a short random suffix (`crypto.randomUUID().slice(0,8)`). Ideal: use `nanoid`/UUID and drop the human-readable timestamp from the ID (keep it in a separate `addedAt` field).

### 1.6 HIGH — Client-side `handleCheckboxChange` double-writes
**Location:** `client/src/components/OrderDeliveryCard.jsx`, `OrderDeliveredCard.jsx`, `CollectOrderForm.jsx:47-68`
**Description:** Each checkbox invokes `updateOrder` inside a `setState` callback, then `window.location.reload()` after 3 s. If the user clicks two checkboxes quickly, each `setState` works from pre-write state, so the second write overwrites the first (lost-delivery bug). A queue of timed reloads also compounds.
**Recommendation:** Serialise writes through a `useRef` promise chain or a server-side "PATCH items" endpoint that accepts a single item-ID toggle (so each click is independent) and returns the canonical items array.

### 1.7 MEDIUM — Duplicate `createdAt` alias in `getOrders`
**Location:** `server/controllers/orders.controllers.js:15, 29-34, 62-67`
**Description:** The SELECT list contains `CONVERT_TZ(...)` un-aliased *and* `DATE(CONVERT_TZ(...)) as createdAt` → result row has two `createdAt` keys; only the last one survives, so the frontend never receives the *time* portion (only the date). Multiple pages rely on `order.createdAt` believing it's a timestamp.
**Recommendation:** Alias distinctly: `… as createdAtTs, DATE(…) as createdAtDate`, then update consumers.

### 1.8 MEDIUM — Unreachable code in `UserProvider.autenticateUser`
**Location:** `client/src/context/UserProvider.jsx:23-24`
**Description:** `return response.data;` is followed by `setUser(response.data);` — the setter never runs, so `user` context never populates on successful login. Any code relying on `useUser().user` silently sees `null`.
**Recommendation:** Reorder: `setUser(…)` then `return …`.

### 1.9 MEDIUM — `order.paid` toggled 1 → 0 leaves stale `paidAt`
**Location:** `client/src/pages/CollectOrderForm.jsx:211-217`, `server/controllers/deposits.controllers.js:134`
**Description:** `deleteDeposit` sets `paid = 0` but does not `paidAt = NULL`. A subsequent report of "orders paid on date X" may still match via `DATE(paidAt)=X AND paid=0` if queries drift.
**Recommendation:** Always pair `paid=0` with `paidAt=NULL`. On client-side update, `…(values.paid === 1 ? {paidAt: fechaActual} : {paidAt: null})`.

### 1.10 LOW — Dead/unused code
**Location:** various
- `client/src/pages/CollectOrderForm.jsx:529-539` — commented "Cobrar Total" button
- `server/routes/index.routes.js:2` — unused `pool` import
- `pages/_archived/CollectedOrdersPage.jsx` — archive still imported nowhere, OK to delete

**Recommendation:** Delete — version control preserves history.

### 1.11 LOW — SOLID drift
**Description:** Controllers concatenate SELECT strings, parse JSON in-place, and mix query + business-logic + response shaping. No repository/service layer. As endpoints grow, duplication of `CONVERT_TZ` logic and column lists will compound (already 6 identical timezone expressions across orders.controllers).
**Recommendation:** Extract a small DAO (`orderRepo.getWithClient(id)`) and a timezone helper (`tzColumn('orders.createdAt')`).

## 2. RACE CONDITIONS, SECURITY, UNSAFE PRACTICES

### 2.1 CRITICAL — Passwords transmitted in URL, stored in plaintext
**Location:** `server/routes/users.routes.js`, `server/controllers/users.controllers.js`, `client/src/api/users.api.js`
**Description:** `GET /users/:userName/:pass` — passwords land in Render access logs, browser history, Referer headers, and every proxy in between. The DB comparison is plaintext (no bcrypt).
**Recommendation:**
1. Replace with `POST /auth/login` taking `{username, password}` in JSON.
2. bcrypt-hash stored passwords (one-off migration script to re-hash all existing rows on first login).
3. Issue a signed JWT / session cookie (httpOnly, Secure, SameSite=Lax).
4. Rate-limit (`express-rate-limit`, 5 attempts / 15 min / IP).

### 2.2 CRITICAL — Auth state is a single `localStorage` string
**Location:** `client/src/pages/LoginForm.jsx:23`
**Description:** `localStorage.setItem('user', response.userName)`. Any browser-console user can set this to `"admin"` and get the full navigation menu. The backend never re-validates; the API has no auth middleware at all.
**Recommendation:** Move the session to an httpOnly cookie bearing a JWT. Add an `authRequired` Express middleware and apply it to every route except `/auth/login` and `/factura/:id` (public invoice).

### 2.3 HIGH — `/query` endpoint is unauthenticated
**Location:** `server/controllers/query.controllers.js`, `server/routes/query.routes.js`
**Description:** Anyone on the internet can `POST /query {"query":"SELECT * FROM clients"}` and receive the entire customer table (1000 rows at a time). The filter allows SELECT/SHOW/DESCRIBE/EXPLAIN and blocks semicolons/mutations (good), but there is *no* auth check. Regex blocklist could also be bypassed with things like `INFORMATION_SCHEMA` enumeration, which is permitted. This is the #1 data-exfiltration risk.
**Recommendation:** Require admin auth + IP allow-list. Remove entirely in favour of dashboards fed by whitelisted aggregate endpoints. Log every executed query with user + IP.

### 2.4 HIGH — Hardcoded "master password" in frontend
**Location:** `client/src/pages/OrdersPage.jsx:48`
**Description:** `if (clave === '031421') { …show all orders… }`. Shipped in every client bundle on Render; anyone reading the JS sees it.
**Recommendation:** Remove the secret from the client. Gate sensitive views via backend role check.

### 2.5 HIGH — DB credentials and Resend API key in `.env.local`
**Location:** `.env.local` (project root — not committed on `main` but present in worktree)
**Description:** Live DigitalOcean DB password and Resend API key in plaintext file. If the file is ever committed or the worktree archived, secrets leak. Rotation story is unclear.
**Recommendation:** Confirm `.env.local` is in `.gitignore` (verify). Treat Render env-var console as the source of truth; rotate credentials now if this file has ever been pushed or shared.

### 2.6 HIGH — CORS includes `localhost`
**Location:** `server/index.js:21-28`
**Description:** Production CORS allow-list contains `http://localhost:5173` and `http://localhost:25060`. With `credentials: true`, a malicious page served locally (e.g. a dev's machine during a pentest / hostile wi-fi) can drive authenticated requests.
**Recommendation:** Split configs: prod origins from env var `ALLOWED_ORIGINS`, dev values only in `.env.development`.

### 2.7 HIGH — No input validation on write endpoints
**Location:** all `createX` / `updateX` in controllers (e.g. `orders.controllers.js:199-246`, `clients.controllers.js`, `products.controllers.js`)
**Description:** `INSERT INTO deposits SET ?` trusts `req.body` keys outright. An attacker can inject `isDeleted: 1` or arbitrary columns on create. Missing checks on types, lengths, foreign-key existence.
**Recommendation:** Add `zod` / `joi` schemas per endpoint. Whitelist allowed body keys. Reject unknown fields.

### 2.8 MEDIUM — SQL-injection surface is small but non-zero
**Description:** All queries inspected use placeholders (`?`). The `/query` endpoint is the only dynamic SQL, and it has a deny-list (regex). Risk: regex bypass via obscure syntax (`/*!50000 DROP */` MySQL version-conditional comments). It currently strips comments *before* the keyword scan, which blunts this.
**Recommendation:** Still prefer allow-list (read-only replica role on DB side) over regex filtering.

### 2.9 MEDIUM — Error responses leak SQL state
**Location:** `deposits.controllers.js:64-67` returns `error.message` and `error.sqlMessage`.
**Description:** Reveals table/column names and MySQL version to any caller.
**Recommendation:** Return `{message: 'Error procesando depósito'}` to the client; keep stack trace in the error log / Resend email only.

### 2.10 MEDIUM — No CSRF protection
**Description:** With the move to cookie-based auth (2.1/2.2), CSRF becomes relevant. Current `localStorage` setup is XSS-susceptible but not CSRF-susceptible.
**Recommendation:** Post-migration, add `csurf` or a double-submit-cookie pattern on mutating routes.

### 2.11 LOW — XSS surface is small
**Description:** No `dangerouslySetInnerHTML` anywhere in `client/src`. React auto-escapes; product/client names render safely.
**Recommendation:** No action; retain the zero-`dangerouslySetInnerHTML` policy.

## 3. BUSINESS LOGIC vs DOCUMENTATION

### 3.1 HIGH — One-unpaid-order-per-client is best-effort (see §1.3)
Documented as a hard rule, enforced only in client code.

### 3.2 HIGH — `collectedBy` audit trail is wrong (see §1.4)
Documented as "Known Bug" but still shipped.

### 3.3 MEDIUM — Order merge silently mixes delivered & undelivered items
**Location:** `client/src/pages/OrderForm.jsx:149-157`
**Description:** Merging into an existing unpaid order concatenates cart items into the items JSON without surfacing that previously-delivered items are now commingled with new undelivered ones. A driver may accidentally re-deliver or skip.
**Recommendation:** Before merge, show a confirmation modal listing existing items + their delivery status, require explicit confirmation. Consider forbidding merges when ≥1 existing item is already delivered.

### 3.4 MEDIUM — Abandoned order can be re-activated with stale items
**Location:** `server/controllers/orders.controllers.js` (`abandon` / `reactivate`)
**Description:** Reactivation clears `abandonedAt/By/Reason` but leaves items with potentially outdated prices. If product prices changed during abandonment, the order holds the old unitValue.
**Recommendation:** On reactivate, refresh each item's `unitValue` from the current `products` table or show a "prices changed" warning.

### 3.5 LOW — Hard delete of orders contradicts soft-delete pattern used elsewhere
**Location:** `DELETE /order/:id`
**Description:** Deposits and clients use `isDeleted=1`; orders are hard-deleted. This asymmetry loses financial audit trail when an order is removed.
**Recommendation:** Add `isDeleted/deletedAt/deletedBy` to `orders` and switch the DELETE endpoint to soft delete.

## 4. USER-ERROR PREVENTION

### 4.1 HIGH — Deposit input accepts negative / non-numeric values
**Location:** `client/src/pages/CollectOrderForm.jsx:464-527`
**Description:** `type="number"` is the only guard; no `min`, `max`, `step`, no Formik `validate`. A negative deposit would decrease `order.deposit` and inflate debt.
**Recommendation:** `min={0} max={calculateTotal() - order.deposit} step="1"` + Formik validator that returns `errors.deposit` before allowing submit.

### 4.2 HIGH — No confirmation on several irreversible ops
- Order delete (hard delete)
- Client delete
- Product delete

Documentation says "Confirmations for irreversible operations" is standard — several destructive routes lack it.
**Recommendation:** Audit every DELETE-triggering button and wrap with `Modal.confirm` (Ant Design).

### 4.3 MEDIUM — `type="button"` regression risk
**Description:** CLAUDE.md flags this as a historic bug. Without a lint rule, it will recur.
**Recommendation:** Add an ESLint rule or codemod check: any `<button>` inside a `<form>` without `type="submit"` must have `type="button"`.

### 4.4 MEDIUM — Phone / premises / name fields have no format validation
**Location:** `client/src/pages/ClientForm.jsx`
**Description:** Phone can contain letters, premises can be `"Abc def"` breaking `CAST(clients.premises AS SIGNED)` ORDER BY — which silently coerces non-numeric to 0 in MySQL.
**Recommendation:** Regex-validate phone, numeric-only validate premises, enforce length caps (§5.2).

### 4.5 MEDIUM — Clicking the payment confirm button twice is possible
**Location:** `CollectOrderForm.jsx:169-258`
**Description:** `setIsRegistering(true)` disables the button, but the 2 s `setTimeout` before reload is the only other guard. With a slow backend, a second click during the gap could re-fire the modal confirm → duplicate deposit.
**Recommendation:** `useRef(false)` flag set at handler entry; early-return on subsequent invocations. Or use an idempotency key sent to the backend.

### 4.6 LOW — Whitespace / trim missing on inputs
**Description:** Login accepts `"david "` vs `"david"` as different users. Client names too.
**Recommendation:** `.trim()` on submit in all forms.

## 5. DATA SCALABILITY

### 5.1 CRITICAL — `orders.items` JSON-in-TEXT is the #1 scale bottleneck
**Location:** `server/controllers/orders.controllers.js:43, 76-77`
**Description:** Delivery-tracking queries use `LIKE '%"delivered":false%'` against a TEXT column → full table scan on every `/notDeliveredOrders` and `/deliveredOrders/:date` call. No index can help. At 100 k orders the scan alone will dominate response time. TEXT max is 64 KB; a cart with ≥50 verbose items approaches the limit; writes will silently truncate if not watched.
**Recommendation:** Normalize to a dedicated `order_items` table:
```sql
CREATE TABLE order_items (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  orderId       INT NOT NULL,
  productId     INT NOT NULL,
  quantity      INT NOT NULL,
  unitValue     INT NOT NULL,
  delivered     TINYINT(1) NOT NULL DEFAULT 0,
  deliveredAt   DATE NULL,
  addedAt       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_order (orderId),
  INDEX idx_delivered (delivered),
  INDEX idx_deliveredAt (deliveredAt),
  FOREIGN KEY (orderId) REFERENCES orders(id) ON DELETE CASCADE,
  FOREIGN KEY (productId) REFERENCES products(id)
);
```
Plan a dual-write + backfill migration. Allow 1-2 sprints; this is the largest single change.

### 5.2 HIGH — Text columns are both too tight (client fields) and unbounded (abandonReason)
**Description:** `clients.clientName VARCHAR(20)` and `clients.premises VARCHAR(20)` truncate realistic input silently. `orders.abandonReason` is TEXT with no application-level length cap — a user can submit 64 KB per record.
**Recommendation:**
```sql
ALTER TABLE clients MODIFY clientName VARCHAR(100);
ALTER TABLE clients MODIFY premises VARCHAR(50);
ALTER TABLE clients MODIFY mall VARCHAR(100);
ALTER TABLE products MODIFY productName VARCHAR(200);
ALTER TABLE orders MODIFY abandonReason VARCHAR(1000);
ALTER TABLE orders MODIFY collectedBy VARCHAR(100);
```
…and enforce caps in the controllers (zod `max(n)`).

### 5.3 HIGH — Missing indexes on hot-path columns
**Description:** Code grep of every WHERE/ORDER BY reveals these unindexed columns: `orders.paid`, `orders.clientId`, `orders.isAbandoned`, `orders.paidAt`, `deposits.orderId`, `deposits.isDeleted`, `deposits.depositCreatedAt`, `clients.mall`, `clients.isDeleted`.
**Recommendation:** (read-only now; run as ALTER during a maintenance window)
```sql
CREATE INDEX idx_orders_paid_abandoned ON orders(paid, isAbandoned);
CREATE INDEX idx_orders_clientId_paid ON orders(clientId, paid);
CREATE INDEX idx_orders_paidAt ON orders(paidAt);
CREATE INDEX idx_deposits_orderId_isDeleted ON deposits(orderId, isDeleted);
CREATE INDEX idx_deposits_createdAt ON deposits(depositCreatedAt);
CREATE INDEX idx_clients_mall_isDeleted ON clients(mall, isDeleted);
```
Use the read-only `/query` endpoint or local `.env`-connected client to confirm `EXPLAIN` plans before deployment.

### 5.4 HIGH — No foreign-key constraints
**Description:** `orders.clientId`, `deposits.orderId`, `deposits.clientId` are soft references. `/orphanedOrders` endpoint exists specifically to clean up data that FKs would have prevented. Cascade behaviour is undefined.
**Recommendation:** After backfilling orphans, add `FOREIGN KEY … ON DELETE RESTRICT` (or `CASCADE` for deposits per business call).

### 5.5 MEDIUM — Deposits table has no archival / purge
**Description:** Soft-deleted deposits (`isDeleted=1`) are never purged; every query pays the scan tax forever.
**Recommendation:** Monthly job: move rows where `isDeleted=1 AND deletedAt < NOW() - INTERVAL 1 YEAR` to `deposits_archive`. Add `WHERE isDeleted=0` to `getDeposits` (currently missing — line 6).

### 5.6 MEDIUM — `getDeposits` returns every row ever
**Location:** `server/controllers/deposits.controllers.js:4-12`
**Description:** No `WHERE`, no `LIMIT`. At 300 k rows this response is hundreds of MB.
**Recommendation:** Paginate (`LIMIT ? OFFSET ?`) or force a date-range filter.

### 5.7 MEDIUM — Proposed entity limits
| Entity | Proposed max | Enforcement |
|---|---|---|
| Items per order | 50 | Reject at `POST /order` / `PUT /order/:id` |
| Deposits per order | 100 | Reject at `POST /deposits` |
| abandonReason | 500 chars | zod `max(500)` + VARCHAR(1000) buffer |
| clientName | 100 chars | VARCHAR + zod |
| productName | 200 chars | VARCHAR + zod |

## 6. OPTIMIZATION & PERFORMANCE

### 6.1 HIGH — N+1 in `deleteDeposit` recalc loop
See §1.1. One `UPDATE … CASE` replaces N round-trips.

### 6.2 HIGH — JSON LIKE full table scans
See §5.1. The normalization is the only real fix; in the meantime, add `orders.paid=0` to the scan-heavy queries first so MySQL can filter on the smaller working set (partial mitigation — `paid=0` should itself be indexed first per §5.3).

### 6.3 HIGH — `window.location.reload()` used as a poor-man's state sync
**Location:** `CollectOrderForm.jsx:107, 252`, `OrderDeliveryCard.jsx`, `OrderDeliveredCard.jsx`
**Description:** Every payment / deposit delete / checkbox toggle reloads the entire SPA. Every provider refetches. On slow mobile networks over the Unilago wifi, this is 3-10 s of dead screen.
**Recommendation:** Refetch only the affected order (`loadOrder(params.id)`) and let context providers update in place. Remove `setTimeout(() => window.location.reload(), 2000)`.

### 6.4 MEDIUM — `sumarDepositos` recomputed on every render
**Location:** `client/src/pages/DepositedOrdersPage.jsx`
**Description:** O(n) aggregation runs on every keystroke / filter change over the full list.
**Recommendation:** `useMemo(() => sumarDepositos(filtered), [filtered])`.

### 6.5 MEDIUM — `SELECT *` everywhere
**Description:** Most controller SELECTs drag every column, including TEXT `items`. Every list endpoint pays the cost.
**Recommendation:** Enumerate columns. Endpoints like `/orders/` that return counts for dashboards don't need `items` at all.

### 6.6 MEDIUM — No pagination on high-growth endpoints
`/orders`, `/deposits`, `/abonos`, `/clients` all return the entire table. At current volumes (~10 k rows) load is tolerable, but mobile memory limits will hit before the server does.
**Recommendation:** Add `?page=1&pageSize=50` everywhere a list drives UI.

### 6.7 LOW — Duplicate onClick on card buttons
**Location:** `client/src/components/OrderCollectCard.jsx:64-76`
**Description:** Both the button and the inner icon have an onClick. Navigation fires twice; no user-visible damage because React batches the nav, but wasteful.
**Recommendation:** Remove the icon-level handler.

## 7. OPERATIONAL CONSTRAINTS (READ-ONLY AUDIT POSTURE)

Because the production DB is read-only for this audit, **none of the fixes above are applied** yet. The following is the read-only verification I recommend the team run (from a local terminal with `.env` pointing at the prod replica or via the existing `/query` endpoint with the caveats in §2.3):

### 7.1 Verification queries
```sql
-- Confirm scan-heavy queries are actually scanning
EXPLAIN SELECT * FROM orders
WHERE paid = 0 AND items LIKE '%"delivered":false%';

-- Confirm missing indexes
SHOW INDEXES FROM orders;
SHOW INDEXES FROM deposits;
SHOW INDEXES FROM clients;

-- Sanity-check magnitude of §5.1 risk: largest items payload
SELECT id, LENGTH(items) AS size_bytes
FROM orders ORDER BY size_bytes DESC LIMIT 10;

-- How many orphaned orders today (§5.4)?
SELECT COUNT(*) FROM orders o
LEFT JOIN clients c ON o.clientId = c.id
WHERE c.id IS NULL;

-- Paid-without-paidAt (§1.9)
SELECT COUNT(*) FROM orders WHERE paid = 1 AND paidAt IS NULL;
SELECT COUNT(*) FROM orders WHERE paid = 0 AND paidAt IS NOT NULL;

-- Duplicate active unpaid orders per client (§1.3)
SELECT clientId, COUNT(*) c FROM orders
WHERE paid = 0 AND (isAbandoned = 0 OR isAbandoned IS NULL)
GROUP BY clientId HAVING c > 1;

-- Deposits vs order.deposit drift (§1.1 / §1.2)
SELECT o.id, o.deposit AS order_deposit,
       COALESCE(SUM(d.depositValue), 0) AS sum_active
FROM orders o
LEFT JOIN deposits d ON d.orderId = o.id AND d.isDeleted = 0
GROUP BY o.id
HAVING order_deposit <> sum_active
LIMIT 100;

-- collectedBy values that are actually mall names (§1.4)
SELECT collectedBy, COUNT(*) FROM orders
WHERE collectedBy IN ('Unilago','Alta Tecnología','Cliente Frecuente','Otros')
GROUP BY collectedBy;
```

These give a one-page **risk-quantification report** without mutating state.
