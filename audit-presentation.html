Problema 1.1 — deleteDeposit no es transaccional

CRITICAL Dinero no reconciliable entre la tabla deposits y orders.deposit

📂 server/controllers/deposits.controllers.js:71–146

¿Qué hace deleteDeposit?

Cuando el usuario elimina un depósito incorrecto, el código ejecuta 4 queries independientes sobre el pool compartido:

1
SELECT el depósito (para ver si existe y no está ya borrado)
2
UPDATE deposits SET isDeleted = 1 (soft delete)
3
SELECT todos los depósitos activos de esa orden
4
Loop UPDATE deposits uno por uno recalculando lastDeposit / newDeposit / dueOnDeposit
5
UPDATE orders SET deposit = runningTotal
⚠️ Ninguna de estas queries está envuelta en BEGIN/COMMIT. Cada una usa una conexión del pool, posiblemente DIFERENTE conexión cada vez.

1.1 — Escenario real que corrompe datos

📖 Contexto: Orden con 3 depósitos
DepósitodepositValuenewDeposit (cumulativo)
#1$20,000$20,000
#2$15,000$35,000
#3$10,000$45,000

orders.deposit en la tabla orders: $45,000

Operación: el usuario elimina el depósito #2

1
Step 4: UPDATE — depósito #2 marcado como eliminado ✓
2
Step 5: SELECT — devuelve depósitos #1 y #3
3
Step 6: UPDATE depósito #1 (sin cambios, runningTotal=$20,000)
💥
El servidor crashea aquí (OOM, connection reset, timeout del pool de Render, etc.)
Estado resultante en la base de datos:
  • ❌ Depósito #2: isDeleted = 1 (borrado)
  • ❌ Depósito #3: newDeposit = $45,000 (VIEJO, nunca recalculado)
  • ❌ orders.deposit: $45,000 (NUNCA actualizado al Step 9)
La suma de depósitos activos ($20k + $10k = $30k) NO coincide con orders.deposit ($45k). Dinero fantasma de $15,000.

1.1 — Más formas de romperlo (sin crash de servidor)

🔸 Concurrencia: dos usuarios, misma orden

Escenario: Usuario A borra depósito #2 mientras Usuario B crea un depósito nuevo
TiempoUsuario A (delete)Usuario B (create)
T0SELECT activos → [#1, #2, #3]—
T1UPDATE #2 isDeleted=1—
T2SELECT activos → [#1, #3]INSERT deposit #4 (basado en orders.deposit viejo)
T3Loop recalcula solo #1 y #3UPDATE orders SET deposit = $45k + nuevo
T4UPDATE orders SET deposit = $30k ← PISA el update de B—
⚠️ El depósito #4 de Usuario B quedó registrado, pero orders.deposit terminó con el valor que escribió A (basado en una foto vieja de la tabla). Dinero perdido.

🔸 Pool connection drops

Render.com recicla conexiones a MySQL (DigitalOcean) cuando hay idle timeout. Cada pool.query() puede tomar una conexión diferente. Si el pool drop-ea entre Step 4 y Step 5, el error queda silencioso (el pool reconecta solo) pero los updates posteriores trabajan con datos inconsistentes.

1.1 — Solución

✅ Paso 1: Transacción con una sola conexión

export const deleteDeposit = async (req, res) => {
    const conn = await pool.getConnection();
    try {
        await conn.beginTransaction();

        const [depositResult] = await conn.query("SELECT ...");
        await conn.query("UPDATE deposits SET isDeleted=1 ...");
        ...
        // Reemplaza el loop N+1 con UN solo UPDATE con CASE:
        await conn.query(`
            UPDATE deposits
            SET lastDeposit = CASE depositId WHEN ? THEN ? WHEN ? THEN ? END,
                newDeposit  = CASE depositId WHEN ? THEN ? WHEN ? THEN ? END,
                dueOnDeposit= CASE depositId WHEN ? THEN ? WHEN ? THEN ? END
            WHERE depositId IN (?, ?)
        `, [...]);

        await conn.query("UPDATE orders SET deposit=? ...");

        await conn.commit();
        res.json({ message: "OK" });
    } catch (error) {
        await conn.rollback();   // ← RESTAURA todo si algo falla
        res.status(500).json({ message: "Error" });
    } finally {
        conn.release();                // ← Devuelve conexión al pool
    }
};

Beneficios:

  • Atomicidad — o se completan TODOS los pasos, o NINGUNO.
  • Aislamiento — Usuario B no ve estado intermedio de Usuario A.
  • Performance — un UPDATE con CASE reemplaza N updates (menos round-trips a MySQL).

Problema 1.2 — createDeposit no transaccional con la orden

CRITICAL Depósitos "huérfanos" que no actualizan la orden

📂 server/controllers/deposits.controllers.js:42–69
📂 client/src/pages/CollectOrderForm.jsx:219–233

Flujo actual (frontend hace 2 llamadas separadas)

1
Frontend: await createDeposit(neewDeposit) — POST /deposits → INSERT
2
Frontend: await updateOrder(id, { deposit, paid, paidAt }) — PUT /order/:id → UPDATE
⚠️ Son 2 requests HTTP independientes. Si el primero tiene éxito y el segundo falla (red, timeout, servidor reiniciado), queda una fila en deposits pero orders.deposit sigue viejo.

1.2 — Escenario real

📖 Mesera en Unilago cobra $30,000 a un cliente
1
Mesera teclea $30,000, confirma
2
POST /deposits → INSERT OK. Fila creada con depositValue=30000.
📶
El wifi del mall se cae por 8 segundos (común en Unilago).
3
PUT /order/:id → TIMEOUT. El cliente dispara el catch y muestra "Error procesando el pago".
4
Mesera ve el error, reintenta. El sistema muestra la orden con deuda todavía de $30,000 (porque orders.deposit nunca se actualizó).
5
Mesera registra el pago otra vez: POST /deposits → INSERT OK #2. PUT /order/:id → esta vez sí funciona.
Resultado:
  • 2 filas en deposits de $30,000 cada una ($60,000 total)
  • orders.deposit = $30,000 (solo el segundo UPDATE contó)
  • El reporte diario /cobrosHoy muestra $60,000 cobrados porque suma la tabla deposits
  • La caja real solo tiene $30,000
  • Al borrar uno de los depósitos duplicados, el recálculo de 1.1 falla porque las sumas no cuadran

1.2 — Solución: un solo endpoint atómico

✅ Mover toda la lógica al servidor en UNA transacción

// Nueva ruta: POST /orders/:id/deposits
export const addDepositToOrder = async (req, res) => {
    const conn = await pool.getConnection();
    try {
        await conn.beginTransaction();

        // 1) Traer la orden y bloquearla hasta el COMMIT
        const [[order]] = await conn.query(
            "SELECT * FROM orders WHERE id = ? FOR UPDATE",
            [req.params.id]
        );
        if (!order || order.paid === 1) throw new Error("Orden ya pagada");

        // 2) Validar montos (no permitir sobrepago)
        const total = calculateOrderTotal(order.items);
        const remaining = total - order.deposit;
        if (req.body.depositValue > remaining) throw new Error("Monto excede saldo");

        // 3) INSERT deposit
        await conn.query("INSERT INTO deposits SET ?", {
            orderId: order.id,
            clientId: order.clientId,
            depositValue: req.body.depositValue,
            lastDeposit: order.deposit,
            newDeposit: order.deposit + req.body.depositValue,
            ...
        });

        // 4) UPDATE order en la MISMA transacción
        const newDeposit = order.deposit + req.body.depositValue;
        const isPaid = newDeposit >= total ? 1 : 0;
        await conn.query(
            "UPDATE orders SET deposit=?, paid=?, paidAt=? WHERE id=?",
            [newDeposit, isPaid, isPaid ? today() : null, order.id]
        );

        await conn.commit();
        res.json({ success: true, paid: isPaid });
    } catch (error) {
        await conn.rollback();
        res.status(500).json({ message: error.message });
    } finally { conn.release(); }
};

Frontend pasa de 2 llamadas a 1 llamada: await addDeposit(orderId, { depositValue, paymentMethod }). Si falla, nada quedó en la DB. Problema resuelto.

Problema 1.7 — Alias duplicado createdAt

MEDIUM El frontend pierde la hora de creación de las órdenes

📂 server/controllers/orders.controllers.js:15 (getOrders)
📂 Y se repite en líneas 34, 67, 147, 159, 259 (6 queries afectadas)

El bug

La consulta SELECT lista DOS columnas con el alias createdAt. MySQL las devuelve ambas, pero cuando el driver mysql2 las convierte a JavaScript object, las claves se colapsan en la última.

1.7 — Código real del bug

server/controllers/orders.controllers.js:15 (getOrders):

SELECT
  orders.id,
  orders.deposit,
  CONVERT_TZ(orders.createdAt, '+00:00', '-05:00'),       -- ← sin alias explícito, MySQL usa "CONVERT_TZ(...)"
  orders.clientId,
  orders.paid,
  orders.collectedBy,
  orders.items,
  DATE(CONVERT_TZ(orders.createdAt, '+00:00', '-05:00')) as createdAt,  -- ← ESTE gana
  clients.premises,
  clients.clientName,
  clients.mall
FROM orders
JOIN clients ON orders.clientId = clients.id
WHERE orders.paid = 0 ...

Lo que devuelve la query vs lo que recibe el frontend

Columna SQLAlias resultanteValor
CONVERT_TZ(...)"CONVERT_TZ(orders.createdAt, '+00:00', '-05:00')""2026-04-22 17:08:30"
DATE(CONVERT_TZ(...))"createdAt""2026-04-22"

El frontend accede a order.createdAt y recibe solo la fecha sin la hora. La columna del timestamp con hora queda bajo un nombre largo y feo que nadie lee.

1.7 — Impacto: el bug del order.createAt

🔴 Este problema se compone con otro bug latente: 6 componentes del frontend leen order.createAt (sin la 'd') en vez de order.createdAt.

Componentes afectados (verificado con Grep):

client/src/components/ClientCard.jsx:56        <span>{client.createAt}</span>
client/src/components/DepositsCard.jsx:19      <span>{formatDate(order.createAt)}</span>

client/src/components/OrderDeliveredCard.jsx:50 <span>{formatDate(order.createAt)}</span>
client/src/components/OrderDeliveryCard.jsx:50  <span>{formatDate(order.createAt)}</span>

¿Qué pasa en producción?

  • order.createAt → undefined (JavaScript no tira error, solo renderiza "")
  • formatDate(undefined) → dayjs() interpreta undefined como "ahora" y renderiza la fecha de hoy.

Resultado: en muchas tarjetas aparece la fecha del día corriente, no la fecha real de la orden. Nadie lo notó porque las órdenes abiertas son recientes.

Estado real: El bug 1.7 impide acceder a la hora, y además hay un typo que impide leer la fecha correcta. Los dos bugs juntos hacen que esas tarjetas muestren basura.

1.7 — Solución (dos pasos)

✅ Paso 1: Aliases explícitos y distintos en el SQL

SELECT
  orders.id,
  orders.deposit,
  CONVERT_TZ(orders.createdAt, '+00:00', '-05:00') AS createdAtTs,   -- timestamp con hora
  orders.clientId,
  orders.paid,
  orders.items,
  DATE(CONVERT_TZ(orders.createdAt, '+00:00', '-05:00')) AS createdAtDate, -- solo fecha
  clients.premises,
  clients.clientName,
  clients.mall
FROM orders ...

Aplicar en las 6 queries (líneas 15, 34, 67, 147, 159, 259 de orders.controllers.js).

✅ Paso 2: Corregir el typo en 6 componentes

-  <span>{formatDate(order.createAt)}</span>
+  <span>{formatDate(order.createdAtDate)}</span>

-  <span>{order.createAt}</span>
+  <span>{order.createdAtTs}</span>   // cuando quieras hora + fecha

Regla general para evitar que vuelva a pasar:

  • Nunca usar el mismo alias dos veces en un SELECT.
  • Prohibir columnas sin alias explícito cuando se usan funciones (CONVERT_TZ, DATE, etc.).
  • Agregar una regla de lint o un test de contrato que fallen si la API devuelve keys duplicadas.
